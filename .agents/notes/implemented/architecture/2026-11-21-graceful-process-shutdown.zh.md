# Agent Note：进程关闭是一条幂等、先持久化的序列

Status: implemented

[English](2026-11-21-graceful-process-shutdown.md) | 中文

## Problem

一次终端中断会不止一次地到达长期运行的应用。终端向整个前台进程组发送信号，包管理器包装层又把同一个信号转发给它的子进程，因此一次 Ctrl-C 会在同一毫秒内向应用投递两个 `SIGINT` 事件。控制器的旧规则把“关闭已在进行中时收到的任何信号”当作使用者不耐烦，立即调用 `process.exit`，从而切断了通用的 teardown：待写入的 Session 追加从未刷盘，存储占用没有按序释放，而运行在自己会话中的子进程——程序环境、后台任务、持久终端、外部工具进程——被留成了孤儿。同一条规则还让中断的退出码与 supervisor 随后的终止请求发生竞争。

## Decision

信号只发起一次关闭，绝不再升级它。第一次请求固定退出码，后续信号加入该请求，只有流逝的时间才能强制退出。

关闭按有序阶段运行，这些阶段属于 launcher，因为它拥有信号处理器和根上下文：

1. quiesce：取消正在运行的 turn 并等待其结算，使取消结果在刷盘之前被记录。每个输入界面都要到 teardown 销毁时才停止接收，因此在 barrier 期间被接受的工作仍可能启动 turn；该序列不冻结准入；
2. barrier：刷新每个打开的 Session 写入句柄，也就是持久化服务已经暴露的持久化调用；
3. teardown：销毁应用树，关闭句柄、释放占用，并终止自己拥有的子进程。

硬上限是自第一次请求起的十秒。有序阶段运行到上限之前一秒，这一秒保留给持久化 barrier，随后一秒保留给终止自己拥有的子进程，另外留出少量调度余量；因此停滞的阶段会让位，而不会牺牲这两件仍必须发生的事。如果 barrier 自己用尽了保留时间，日志可能不完整，报告会指出哪个阶段耗尽。开发用 supervisor 等待十二秒，高于硬上限，因此不会在应用仍处于自身截止时间内时把中断转成第二个信号。保留路径结束时，launcher 向标准错误写出一条报告，列出未完成的阶段。致命错误处理器加入同一序列，而不是只销毁应用树，其释放时限覆盖该序列。

## Alternatives considered

**任何第二个信号都强制退出。** 这是已发布行为，也正是缺陷：一次终端中断就是两个信号，因此在 `make`/`pnpm` 下优雅路径永远不可达。

**只在第二个信号与第一个不同时才强制退出。** 在中断之后重新发送终止请求的 supervisor 仍会切断 teardown。

**把升级交给各调用方的超时。** 没有任何界面拥有超时，而信号已经送达。

**可配置的截止时间。** 本变更中考虑过但被否决；固定上限配合待完成报告足以诊断缓慢的 teardown，而 supervisor 宽限是唯一与之耦合的值。

**依赖销毁顺序代替显式 barrier。** 应用树销毁无法保证在强制退出前刷盘持久状态，也不会报告还有什么未完成。

## Consequences

中断始终运行同一序列，因此只要 barrier 在其保留时间内完成，进程退出后 Session 日志仍可读取；当 barrier 自己耗尽时，报告会说明，而不是暗示 teardown 已完成。缓慢阶段可以用一行标准错误诊断，而不是静默截断。截止时间是固定的，所以需要更长时间的机器只能依赖报告而不是配置开关。`dev-web` 在第一个信号后等待十二秒，高于应用的硬上限，因此 supervisor 不会在应用仍处于自身截止时间内时把中断转成第二个信号；这两个值必须一起变动。
